# Описание продукта (Product Overview)

## Что делает продукт
API для сообщений от пользователей
- приём через `POST /api/v1/contact` (имя, телефон, email, комментарий)
- сохранять поступившую информацию
- информировать обе стороны
- предварительная обработка сообщений через ИИ
- дружелюбность: при ошибках отдавать ответы с
- - "верным" HTTP-статусом
- - соответствующим текстом
- устойчивость: защита через Rate Limit
- логирование валидных обращений в файл (канал `feedback_storage`, имитация БД)
- защита `/contact` токеном авторизации (`Authorization: Bearer <API_ACCESS_TOKEN>`) — эндпоинт публичный, при этом дёргает платный AI-шлюз и шлёт письма на настоящий email владельца

### А что не делает
- Не использует неверсионированные пути: **все** маршруты API, включая `health`/`metrics`, идут через `/api/v1/...`, а не только `contact` (как буквально в исходном ТЗ) — версионирование всех путей обязательно в нашем понимании.
- Не логирует буквально **все** запросы: в файл (канал `feedback_storage`) попадают только валидные обращения — невалидные нечего сохранять. Исходное ТЗ не вполне учитывает этот момент — формулировка этого проекта приоритетнее буквальной трактовки исходника.

## Настраиваемые параметры продукта
Значения, которые непосредственно влияют на поведение сервиса (по умолчанию конфигурируются через `.env`):

* **Максимальная длина имени** — по умолчанию 255 символов (`FEEDBACK_NAME_MAX_LENGTH` в `.env`).
* **Максимальная длина комментария** — защита от «простыни», по умолчанию 2000 символов (`FEEDBACK_COMMENT_MAX_LENGTH` в `.env`).
* **Rate limiting** — лимит запросов на отправку формы с одного IP в минуту, по умолчанию 5 (`FEEDBACK_RATE_LIMIT_PER_MINUTE` в `.env`).
* **Токен авторизации `/contact`** — общий секрет, который должен быть передан в заголовке `Authorization: Bearer <токен>` (`API_ACCESS_TOKEN` в `.env`). Без токена или с неверным токеном — `401`.
* **AI Gateway** — базовый URL AI-провайдера (`http://127.0.0.1:8101/openai/v1`) и таймаут запроса к нему.
* **Владелец сайта** — email для уведомлений о новых обращениях (`SITE_OWNER_EMAIL` в `.env`).
* **CORS** — список разрешённых origin'ов, с которых принимаются запросы к API (`CORS_ALLOWED_ORIGINS` в `.env`, через запятую).
* **Очередь уведомлений** — драйвер очереди (по умолчанию имитация синхронным драйвером, с возможностью переключения на `database` через конфигурацию).
* **Хранилище/лог обращений (имитация БД)** — канал Monolog `feedback_storage` (файл `storage/logs/feedback.log`), отдельно от общего `storage/logs/laravel.log`. Сюда попадают только валидные обращения — логировать невалидные запросы отдельно смысла нет, поэтому этот единственный канал закрывает и требование "логирование запросов", и хранение в БД (имитация).

### Основной функционал (`POST /api/v1/contact`):
* **Валидация данных:** Сервис принимает и проверяет данные отправителя (имя, телефон, email и текст сообщения). Предусмотрена защита от передачи сверхбольших текстов («простыней»).
* **Сохранение обращений:** Валидное и санитизированное обращение сразу передаётся в репозиторий для сохранения (на текущем этапе — в структурированный лог Monolog, с возможностью миграции на БД) — **до** AI-анализа.
* **Умный анализ (AI-интеграция):** Уже после сохранения текст комментария прогоняется через AI-сервис, который извлекает структурированные данные (см. `SPECS-AI.md`) и сохраняет их отдельно — само обращение при этом не изменяется. Реализовано и проверено на реальном AI-провайдере.
* **Email-уведомления:** На каждое валидное обращение отправляется два отдельных письма с одинаковым содержанием — владельцу сайта и пользователю (каждое — `To` на один адрес, без `Cc`).
* **Отказоустойчивость (Graceful Fallback):** В случае недоступности или сбоев внешних сервисов AI приложение продолжает штатно работать, корректно сохраняя заявку и отправляя стандартный шаблон ответа.

## Критерии приемки (Acceptance Criteria)

Продукт считается успешно выполненным и готовым к сдаче при выполнении следующих критериев:

### 1. API и Маршрутизация
* [ ] **AC 1.1:** Эндпоинт `POST /api/v1/contact` корректно принимает JSON-запросы с полями `name`, `phone`, `email`, `comment`.
* [ ] **AC 1.2:** При отправке валидных данных сервис возвращает успешный статус (HTTP status 201).

### 2. Валидация и Обработка ошибок
* [ ] **AC 2.1:** Отсутствие обязательного поля — см. таблицу ошибок в `ARCHITECTURE.md` §7.
* [ ] **AC 2.2:** Некорректный формат email — см. таблицу ошибок в `ARCHITECTURE.md` §7.
* [ ] **AC 2.3:** Реализовано ограничение на максимальную длину комментария (защита от «простыни», максимум 2000 символов) — см. таблицу ошибок в `ARCHITECTURE.md` §7.
* [ ] **AC 2.4:** Превышение лимита запросов (rate limiting) — см. таблицу ошибок в `ARCHITECTURE.md` §7.
* [ ] **AC 2.5:** Любая непредвиденная (необработанная) ошибка — см. таблицу ошибок в `ARCHITECTURE.md` §7.
* [ ] **AC 2.6:** Отсутствующий или неверный токен авторизации (`Authorization: Bearer`) — см. таблицу ошибок в `ARCHITECTURE.md` §7.

### 3. Бизнес-логика и AI-обработка
* [ ] **AC 3.1:** Поступающий текст обращения проходит обработку сервисом AI.
* [ ] **AC 3.2:** При сбое AI-сервиса (таймаут, отсутствие ключа, недоступность API) основной сценарий сохраняется без падения приложения (Graceful Fallback).

### 4. Email-уведомления
* [ ] **AC 4.1:** На каждое валидное обращение отправляется письмо владельцу сайта (`To`).
* [ ] **AC 4.2:** Письмо с тем же содержанием отдельно (`To`) отправляется на email пользователя, указанный в обращении.

### 5. Сохранение данных и Логирование
* [ ] **AC 5.1:** Каждое валидное обращение передается в `FeedbackRepository` и фиксируется в отдельном специальном канале Monolog `feedback_storage` в соответствующий файл в папке `storage/logs`, имитирующем запись в БД, с сохранением всех атрибутов. Невалидные запросы в этот канал не попадают.

### 6. Качество кода и Тестирование
* [ ] **AC 6.1:** Архитектура сервиса разделена на слои (Controllers -> Requests -> Services -> Repositories -> DTO).
* [ ] **AC 6.2:** Написанные юнит-тесты успешно проходят без ошибок.
