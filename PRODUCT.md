# Описание продукта (Product Overview)

## Что делает продукт
Бэкенд-сервис для лендинг-презентации разработчика. Сервис предоставляет REST API для обработки обращений, поступающих через форму обратной связи на сайте.

Основная задача сервиса — надежно принимать заявки клиентов, автоматически анализировать и обрабатывать текст обращения с помощью искусственного интеллекта (AI), сохранять поступившую информацию и информировать стороны.

## Параметры продукта
Значения, которые непосредственно влияют на поведение сервиса (по умолчанию конфигурируются через `.env`):

* **Максимальная длина комментария** — защита от «простыни», по умолчанию 2000 символов.
* **Rate limiting** — лимит запросов на отправку формы с одного IP в единицу времени (например, N запросов/минуту и M запросов/час; конкретные значения задаются через `.env`).
* **AI Gateway** — базовый URL AI-провайдера (`http://127.0.0.1:8101/openai/v1`) и таймаут запроса к нему.
* **Владелец сайта** — email для уведомлений о новых обращениях и базовый язык сайта (с ним сравнивается язык входящего обращения, чтобы решить, нужен ли перевод/автоответ на другом языке).
* **CORS** — список разрешённых origin'ов, с которых принимаются запросы к API.
* **Очередь уведомлений** — драйвер очереди (по умолчанию имитация синхронным драйвером, с возможностью переключения на `database` через конфигурацию).
* **Логирование** — путь/канал файла логов и уровень логирования запросов и обращений.
* **Хранилище обращений (имитация БД)** — файл, в который пишет отдельный канал Monolog `feedback_storage` (например, `storage/logs/feedback.log`), отдельно от общего `storage/logs/laravel.log`.

### Основной функционал (`POST /api/v1/contact`):
* **Валидация данных:** Сервис принимает и проверяет данные отправителя (имя, телефон, email и текст сообщения). Предусмотрена защита от передачи сверхбольших текстов («простыней»).
* **Умный анализ (AI-интеграция):** Автоматически определяет язык сообщения. Если язык отличается от языка владельца сайта, сервис переводит текст и генерирует персонализированный ответ на родном языке пользователя. В первом приближении AI Gateway реализован как заглушка (без реального обращения к внешнему AI-провайдеру).
* **Сохранение обращений:** Принятое и обогащенное AI-метаданными сообщение передается в репозиторий для сохранения (на текущем этапе — в структурированный лог Monolog, с возможностью миграции на БД).
* **Отказоустойчивость (Graceful Fallback):** В случае недоступности или сбоев внешних сервисов AI приложение продолжает штатно работать, корректно сохраняя заявку и отправляя стандартный шаблон ответа.

## Критерии приемки (Acceptance Criteria)

Продукт считается успешно выполненным и готовым к сдаче при выполнении следующих критериев:

### 1. API и Маршрутизация
* [ ] **AC 1.1:** Эндпоинт `POST /api/v1/contact` корректно принимает JSON-запросы с полями `name`, `phone`, `email`, `comment`.
* [ ] **AC 1.2:** При отправке валидных данных сервис возвращает успешный статус (HTTP status 201).

### 2. Валидация и Обработка ошибок
* [ ] **AC 2.1:** При отсутствии любого из обязательных полей (`name`, `phone`, `email`, `comment`) сервис возвращает ошибку валидации с HTTP status 422 и понятным JSON-описанием.
* [ ] **AC 2.2:** При передаче некорректного формата email возвращается ошибка валидации (HTTP 422).
* [ ] **AC 2.3:** Реализовано ограничение на максимальную длину комментария (защита от «простыни», максимум 2000 символов).
* [ ] **AC 2.4:** При превышении лимита запросов (rate limiting) с одного IP сервис возвращает ошибку с HTTP status 429 и понятным JSON-описанием.

### 3. Бизнес-логика и AI-обработка
* [ ] **AC 3.1:** Поступающий текст обращения проходит обработку сервисом AI.
* [ ] **AC 3.2:** При сбое AI-сервиса (таймаут, отсутствие ключа, недоступность API) основной сценарий сохраняется без падения приложения (Graceful Fallback).

### 4. Сохранение данных и Логирование
* [ ] **AC 4.1:** Каждое валидное обращение передается в `FeedbackRepository` и фиксируется в отдельном специальном канале Monolog `feedback_storage` в соответствующий файл в папке `storage/logs`, имитирующем запись в БД, с сохранением всех атрибутов.


### 5. Качество кода и Тестирование
* [ ] **AC 5.1:** Архитектура сервиса разделена на слои (Controllers -> Requests -> Services -> Repositories -> DTO).
* [ ] **AC 5.2:** Написанные юнит-тесты успешно проходят без ошибок.
