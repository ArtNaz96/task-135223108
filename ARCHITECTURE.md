# Архитектура модуля обработки обратной связи (Feedback)

## 1. Общее описание
Модуль предназначен для приема, валидации, обработки и сохранения сообщений обратной связи от пользователей. Основной паттерн проектирования основывается на разделении слоёв с использованием анемичной модели предметной области (POPO) для передачи данных.

В рамках текущей итерации в полном объёме прорабатывается только `POST /api/v1/contact`. Эндпоинты `GET /api/v1/health` и `GET /api/v1/metrics` реализуются как заглушки, но роутинг и контроллеры проектируются так, чтобы эти два эндпоинта можно было безболезненно наполнить реальной логикой позже (см. раздел 6).

## 2. Основные компоненты системы

### 2.1. Контроллеры и HTTP-слой
* **`FeedbackController`**: Точка входа для HTTP-запросов формы обратной связи (`POST /api/v1/contact`). Отвечает за маршрутизацию и первичную обработку формы, делегирует всю бизнес-логику в `FeedbackService`.
* **`FeedbackRequest`**: Объект запроса (Laravel `FormRequest`), отвечающий за валидацию входящих данных. Выступает в роли "защитного узла": в частности, именно валидатор этого класса проверяет допустимый размер текста комментария (защита от "простыни" — например, правило `max:` по длине + при необходимости кастомное правило на количество строк/повторы).
* **`HealthController`**: Точка входа для `GET /api/v1/health`. В текущей итерации — заглушка, возвращающая статичный JSON-ответ о работоспособности сервиса.
* **`MetricsController`**: Точка входа для `GET /api/v1/metrics`. В текущей итерации — заглушка, возвращающая статичный/нулевой JSON со структурой будущей статистики.
* или другой подход, соответствующий идиомам Laravel 13

### 2.2. Бизнес-логика
Управление бизнес-логикой осуществляется двумя основными сервисами:
* **`FeedbackService`**: Основной сервис для координации бизнес-правил, обработки обращений и взаимодействия с репозиторием. Из `FeedbackRequest` собирает `Feedback` (POPO), вызывает `AiHandler`, передаёт результат в `FeedbackRepository` и инициирует отправку нотификаций.
* **`AiHandler`**: Сервис интеллектуального анализа текста.
  * определяет язык входящего сообщения;
  * если язык отличается от языка владельца сайта — инициирует перевод через `AiGateway`;
  * **опционально** (помечено в ТЗ как "возможно!"): добавляет тег `locale` в метаданные обращения, чтобы автоответчик мог сгенерировать ответ на языке пользователя;
  * работает через `AiGateway` и соответствующий DTO (`AiRequestDTO` / `AiResponseDTO`);
  * реализует graceful fallback: если `AiGateway` недоступен или вернул ошибку — сервис продолжает работать без перевода/анализа, ошибка логируется, а не пробрасывается наверх.
* **`AiGateway`**:
  * *Текущий статус:* Заглушка (Stub). В текущей реализации просто добавляет строку `AI DONE` первой строкой к тексту обращения (из DTO (Ai<?>)).
  * *Целевая реализация:* HTTP-клиент к OpenAI-совместимому API по адресу `http://127.0.0.1:8101/openai/v1` (адрес конфигурируется через `.env`, не хардкодится).

#### DTO для AI-слоя
* **`AiRequestDTO`**: объект-контейнер данных, передаваемых из `AiHandler` в `AiGateway` (текст обращения, исходный язык владельца сайта и т.п.).
* **`AiResponseDTO`**: объект-контейнер результата от `AiGateway` (обработанный/переведённый текст, определённый `locale`, признак успеха/fallback).

### 2.3. Модель данных
* **`Feedback`**: Анемичная модель данных (POPO — Plain Old PHP Object), описывающая структуру обращения. Формируется на основе данных, прошедших валидацию.
`(имя, телефон, email, комментарий)` - требуемые поля

### 2.4. Слой доступа к данным (Repository)
* **`FeedbackRepositoryInterface`** + **`FeedbackRepository`**: Интерфейс вынесен отдельно, чтобы переход v1 → v2 не требовал правок в вызывающем коде (`FeedbackService` зависит только от интерфейса, конкретная реализация связывается в service-провайдере).
* Отвечает за запись переданной ему модели `Feedback`.
* Предоставляет метод сохранения (например, `save()`, `store()` или `put()`).
  * *Реализация v1 (текущая):* Запись данных осуществляется в соответствующий канал логгера `Monolog`.
  * *Реализация v2 (планируемая):* Переход на полноценную работу с базой данных (БД).
* Предоставляет метод чтения последних X записей (пригодится позже для реальной реализации `GET /api/metrics`).

Соответственно, при реализации следует учесть будущий переход от v1 к v2.

### 2.5. Группа отправления нотификаций
* потребуется минимальная очередь (можно имитацию — например, синхронный или `database`-драйвер очереди Laravel).
* **`SendOwnerFeedbackNotification`** (Job + Mailable): письмо владельцу сайта о новом обращении.
* **`SendUserFeedbackCopy`** (Job + Mailable): копия обращения пользователю, либо (предпочтительный вариант по ТЗ) **`SendAutoReplyMail`** — автоматически сгенерированный ответ на языке пользователя (использует `locale` из `AiResponseDTO`, если он проставлен).
* **`FeedbackNotifier`**: тонкий координирующий сервис, вызываемый из `FeedbackService`, который ставит нужные Job'ы в очередь, не заставляя `FeedbackService` знать детали отправки писем.

### 2.6. Middleware и сквозная функциональность
* **Rate limiting**: защита `POST /api/v1/contact` от спама. Базовый вариант — Laravel-овский `throttle` middleware с файловым/кэш-драйвером лимитера; при необходимости кастомизации — отдельный **`FeedbackRateLimiter`** (именованный лимитер через `RateLimiter::for()`), настраиваемый через `.env`.
* **`RequestLoggingMiddleware`**: логирует все входящие запросы (метод, путь, IP, статус ответа) в отдельный файловый канал логов (`Monolog`), не зависящий от бизнес-лога обращений.
* **CORS**: используется штатный `HandleCors` middleware Laravel + `config/cors.php` (API же — CORS обязателен).
* **Force JSON**: middleware/трейт, гарантирующий, что API всегда отвечает `application/json` (в т.ч. на ошибки валидации/сервера).
* **Глобальный обработчик ошибок**: настраивается в `bootstrap/app.php` (`->withExceptions()`, Laravel 13) — приводит любые исключения (валидация, AI-сбои, прочие) к единому JSON-формату ошибки с корректным HTTP-статусом.

### 2.7. Providers / DI
* **`FeedbackServiceProvider`** (или расширение `AppServiceProvider`): связывает `FeedbackRepositoryInterface` → `FeedbackRepository` (v1, лог-based), регистрирует конфигурацию HTTP-клиента для `AiGateway` (базовый URL, таймаут, ключ — из `.env`/`config/services.php`).

## 3. Юниты для `GET /api/v1/health` (заглушка)
* **`HealthController`**: возвращает статичный JSON вида `{"status": "ok"}` с кодом 200. Реальные проверки (доступность `AiGateway`, запись в хранилище и т.п.) — предмет будущей доработки, интерфейс проектируется так, чтобы их можно было добавить без изменения контракта ответа.

## 4. Юниты для `GET /api/v1/metrics` (заглушка)
* **`MetricsController`**: возвращает статичный/нулевой JSON с ожидаемой структурой статистики (например, число обращений, число ошибок). Реальный сбор статистики (файловый или через `FeedbackRepository`) — предмет будущей доработки.

## 5. Инфраструктура (обязательные требования ТЗ, детальная проработка — позже)
Ниже перечислены только соответствующие юниты/точки расширения — их полная реализация в объём текущей итерации не входит:
* Переменные окружения (`.env`): `AI_GATEWAY_URL`, `AI_GATEWAY_TIMEOUT`, `SITE_OWNER_EMAIL`, `SITE_OWNER_LOCALE`, параметры rate limiting.
* Логирование в файл: отдельные каналы `Monolog` — для обращений (`FeedbackRepository` v1) и для запросов (`RequestLoggingMiddleware`).
* Swagger/OpenAPI документация: аннотации на контроллерах либо отдельный `openapi.yaml`, генерируемый пакетом типа `l5-swagger`.
