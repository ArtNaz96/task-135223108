# Архитектура модуля обработки обратной связи (Feedback)

## 1. Общее описание
Модуль предназначен для приема, валидации, обработки и сохранения сообщений обратной связи от пользователей. Основной паттерн проектирования основывается на разделении слоёв с использованием анемичной модели предметной области (POPO) для передачи данных.

В рамках текущей итерации в полном объёме прорабатывается только `POST /api/v1/contact`. Эндпоинты `GET /api/v1/health` и `GET /api/v1/metrics` реализуются как заглушки, но роутинг и контроллеры проектируются так, чтобы эти два эндпоинта можно было безболезненно наполнить реальной логикой позже (см. раздел 6).

## 2. Основные компоненты системы

### 2.1. Контроллеры и HTTP-слой
* **валидация входных данных**: 
- используем стандартные возможности Laravel по валидации т/ф и почты
- для полей $name и $comment - только длина (обе - из ENV-vars: `FEEDBACK_NAME_MAX_LENGTH`, `FEEDBACK_COMMENT_MAX_LENGTH`)
- все поля обязательные
- **осознанно:** правило `max:` срабатывает на **сыром** значении — санитизация идёт после валидации (см. ниже), поэтому строка ровно из допустимого числа "полезных" символов, но с пробелами/мусором по краям сверх лимита, не пройдёт валидацию. Это ожидаемое поведение, не баг.

* **Санитизация входных данных** — **`App\Support\InputSanitizer::sanitize()`**: 
- только поля $name и $comment - т/ф и почта после валидатора уже или "чистые", или не прошли
- **после** валидации, а не перед (вызывается в `FeedbackController` сразу после `$request->validated()`)
- параноидальная, но не искажающая смысл: убирает управляющие символы (кроме `\n`/`\r`/`\t`) и HTML/script-теги (XSS), схлопывает только горизонтальные пробелы — переносы строк сохраняются, т.к. в письмо должен уйти комментарий "как он пришёл"
- защиту от SQL-инъекций санитизация текста не даёт и не должна — эта защита обеспечивается параметризованными запросами (Eloquent/PDO-биндинги), а не очисткой строк.

* **`FeedbackController`**: Точка входа для HTTP-запросов формы обратной связи (`POST /api/v1/contact`). Отвечает за маршрутизацию и первичную обработку формы, делегирует всю бизнес-логику в `FeedbackService`.
* **`FeedbackRequest`**: Объект запроса (Laravel `FormRequest`), отвечающий за валидацию входящих данных. Выступает в роли "защитного узла": в частности, именно валидатор этого класса проверяет допустимый размер текста комментария (защита от "простыни" — например, правило `max:` по длине + при необходимости кастомное правило на количество строк/повторы).

* **`HealthController`**: Точка входа для `GET /api/v1/health`. В текущей итерации — заглушка, возвращающая статичный JSON-ответ о работоспособности сервиса.
* **`MetricsController`**: Точка входа для `GET /api/v1/metrics`. В текущей итерации — заглушка, возвращающая `501 Not Implemented`.

### 2.2. Бизнес-логика
Управление бизнес-логикой осуществляется двумя основными сервисами:
* **`FeedbackService`**: Основной сервис для координации бизнес-правил, обработки обращений и взаимодействия с репозиторием. Из `FeedbackRequest` собирает `Feedback` (POPO), вызывает `AiHandler`, передаёт результат в `FeedbackRepository` и инициирует отправку нотификаций.
* **`AiHandler`**: Сервис интеллектуального анализа текста.
  * работает через `AiGateway` и соответствующий DTO (`AiRequestDTO` / `AiResponseDTO`);
  * реализует graceful fallback: если `AiGateway` недоступен или вернул ошибку — сервис продолжает работать без анализа, ошибка логируется, а не пробрасывается наверх.
* **`AiGateway`**:
  * *Текущий статус:* Заглушка (Stub). В текущей реализации просто добавляет строку `AI DONE` первой строкой к тексту обращения (из DTO (Ai<?>)).
  * *Целевая реализация:* HTTP-клиент к OpenAI-совместимому API по адресу `http://127.0.0.1:8101/openai/v1` (адрес конфигурируется через `.env`, не хардкодится).

#### DTO для AI-слоя
* **`AiRequestDTO`**: объект-контейнер данных, передаваемых из `AiHandler` в `AiGateway` (текст обращения и т.п.).
* **`AiResponseDTO`**: объект-контейнер результата от `AiGateway` (обработанный текст, признак успеха/fallback).

### 2.3. Модель данных
* **`Feedback`**: Анемичная модель данных (POPO — Plain Old PHP Object), описывающая структуру обращения. Формируется на основе данных, прошедших валидацию и санитизацию (`App\Support\InputSanitizer`, см. §2.1).
`(имя, телефон, email, комментарий)` - требуемые поля
* Дополнительно содержит `id` — генерируется `FeedbackService` по шаблону `YYYYMMDDHHMMSS-<6 случайных цифр>` (дата/время + 6 случайных цифр), сохраняется вместе с остальными атрибутами через `FeedbackRepository`, используется в теме письма владельцу (`Запрос #<id>`).

### 2.4. Слой доступа к данным (Repository)
* **`FeedbackRepositoryInterface`** + **`FeedbackRepository`**: Интерфейс вынесен отдельно, чтобы переход v1 → v2 не требовал правок в вызывающем коде (`FeedbackService` зависит только от интерфейса, конкретная реализация связывается в service-провайдере).
* Отвечает за запись переданной ему модели `Feedback`.
* Предоставляет метод сохранения (например, `save()`, `store()` или `put()`).
  * *Реализация v1 (текущая):* Запись данных осуществляется в отдельный канал `Monolog` — `feedback_storage` (файл `storage/logs/feedback.log`).
  * *Реализация v2 (планируемая):* Переход на полноценную работу с базой данных (БД).
* Предоставляет метод чтения последних X записей (пригодится позже для реальной реализации `GET /api/metrics`).
* В репозиторий (и, соответственно, в этот канал) попадают **только валидные** обращения — `Feedback` (POPO) в принципе не может быть собран из невалидных данных, т.к. собирается уже после прохождения `FeedbackRequest`. Логировать невалидные запросы отдельно смысла нет (нечего сохранять), поэтому отдельного лога "всех запросов подряд" не заводим — один и тот же канал `feedback_storage` одновременно закрывает и требование ТЗ "логирование запросов в файл" (в разумной трактовке — валидных), и неявное требование по "хранению запросов в БД" (в имитации — файловое хранилище).

Соответственно, при реализации следует учесть будущий переход от v1 к v2.

### 2.5. Группа отправления нотификаций
См. **`SPECS-Mail.md`** — вся спецификация по email-уведомлениям (юниты, шаблонизация, содержание письма) вынесена в отдельный файл.

### 2.6. Middleware и сквозная функциональность
* **Rate limiting**: защита `POST /api/v1/contact` от спама. Базовый вариант — Laravel-овский `throttle` middleware с файловым/кэш-драйвером лимитера; при необходимости кастомизации — отдельный **`FeedbackRateLimiter`** (именованный лимитер через `RateLimiter::for()`), настраиваемый через `.env`.
* **CORS**: используется штатный `HandleCors` middleware Laravel + `config/cors.php`.
* **Force JSON**: middleware/трейт, гарантирующий, что API всегда отвечает `application/json` (в т.ч. на ошибки валидации/сервера).
* **Глобальный обработчик ошибок**: настраивается в `bootstrap/app.php` (`->withExceptions()`, Laravel 13) — приводит любые исключения (валидация, AI-сбои, прочие) к единому JSON-формату ошибки с корректным HTTP-статусом. Сам факт ошибки пишется в стандартный лог (`storage/logs/laravel.log`, канал по умолчанию) — отдельно от `feedback_storage`.

### 2.7. Providers / DI
* **`FeedbackServiceProvider`** (или расширение `AppServiceProvider`): связывает `FeedbackRepositoryInterface` → `FeedbackRepository` (v1, лог-based), регистрирует конфигурацию HTTP-клиента для `AiGateway` (базовый URL, таймаут, ключ — из `.env`/`config/services.php`).

## 3. Юниты для `GET /api/v1/health` (заглушка)
* **`HealthController`**: возвращает статичный JSON вида `{"status": "ok"}` с кодом 200. Реальные проверки (доступность `AiGateway`, запись в хранилище и т.п.) — предмет будущей доработки, интерфейс проектируется так, чтобы их можно было добавить без изменения контракта ответа.

## 4. Юниты для `GET /api/v1/metrics` (заглушка)
* **`MetricsController`**: возвращает `501 Not Implemented` — маршрут и контроллер существуют, но реальная логика ещё не реализована. Реальный сбор статистики (файловый или через `FeedbackRepository`) — предмет будущей доработки, после чего ответ сменится на `200` с реальными данными.

## 5. Инфраструктура (обязательные требования ТЗ, детальная проработка — позже)
Ниже перечислены только соответствующие юниты/точки расширения — их полная реализация в объём текущей итерации не входит:
* Переменные окружения (`.env`): `AI_GATEWAY_URL`, `AI_GATEWAY_TIMEOUT`, `SITE_OWNER_EMAIL`, `RATE_LIMIT_CONTACT_PER_MINUTE`, `FEEDBACK_NAME_MAX_LENGTH`, `FEEDBACK_COMMENT_MAX_LENGTH`. (`MAIL_SIGNATURE` больше не используется — подпись теперь часть шаблона письма, см. `SPECS-Mail.md`.)
* Логирование в файл: один канал `Monolog` `feedback_storage` / `storage/logs/feedback.log` — валидные обращения (`FeedbackRepository` v1, имитация БД). Невалидные запросы отдельно не логируются (нечего сохранять); непредвиденные (неконтролируемые) ошибки — забота глобального обработчика ошибок, а не этого канала.
* Swagger/OpenAPI документация: аннотации на контроллерах либо отдельный `openapi.yaml`, генерируемый пакетом типа `l5-swagger`.

## 7. Обработка ошибок — сводная таблица
Единый источник правды по ошибкам `POST /api/v1/contact` — в `PRODUCT.md` соответствующие AC ссылаются сюда, без дублирования деталей.

| Ситуация | Источник | HTTP-статус | Логируется? |
|---|---|---|---|
| Отсутствует обязательное поле (`name`/`phone`/`email`/`comment`) | `FeedbackRequest` (Laravel `ValidationException`) | 422 | нет |
| Некорректный формат email | `FeedbackRequest` (Laravel `ValidationException`) | 422 | нет |
| Комментарий превышает максимальную длину («простыня») | `FeedbackRequest` (Laravel `ValidationException`) | 422 | нет |
| Превышен лимит запросов (rate limiting) | `throttle` / `FeedbackRateLimiter` | 429 | нет |
| Любая непредвиденная (необработанная) ошибка | Глобальный обработчик ошибок (`bootstrap/app.php` → `withExceptions()`) | 500 | да, `storage/logs/laravel.log` |
